# Auth flow

The full login sequence, reverse-engineered by proxy-capturing the official
"Bibliotheek" app one step at a time and confirming each hop before moving
to the next — nothing here was implemented on a guess. See
`docs/odilo-api.md` for the request/response shape of each Odilo call
referenced below.

## The two token tiers

| | App-level token | Patron-level token |
|---|---|---|
| Identifies | the app itself | the signed-in patron |
| Obtained via | static client credentials, no user interaction | real KB SSO login |
| Lifetime | ~24h (`expiresIn: 86400`) | ~4h (`expiresIn: 14399`) |
| Sent as | `Authorization: Bearer <token>` on every request | `OAuth-Token: <token>` on checkout only |
| Refreshed by | calling the token endpoint again with the same static credentials — trivial, already implemented | a `refreshToken` was issued but the refresh call itself is **unconfirmed** (see below) |

The app-level token is not tied to any patron at all — it can be fetched
before anyone logs in, and is what every non-mutating call (search, record
detail, checkouts list) authenticates with. The patron token only gets
added on top for the one endpoint (checkout) that needs to know *who* is
acting.

## Full sequence

```
1. App → Odilo   POST /opac/api/v2/token/
                 Authorization: Basic <app client credentials>
                 body: grant_type=client_credentials
   Odilo → App   { token: <appBearer>, expiresIn: 86400 }
                 Set-Cookie: JSESSIONID, AWSALB, AWSALBCORS
   [OdiloAPIClient.fetchAppToken()]

2. App → Odilo   GET /opac/api/v2/login/external?callback=<scheme>://oauth&client=app&type=OAUTH2
                 Authorization: Bearer <appBearer>   (cookies from #1 auto-attached)
   Odilo → App   "https://login.kb.nl/si/auth/oauth2.0/v1/authorize?client_id=odiloapp&scope=profile+openid
                  &response_type=code&redirect_uri=<callback>&state=<generated>"
                 ← Odilo generates `state` here and remembers it against the JSESSIONID from #1.
                   Neither the app nor KB generates this value — Odilo does, server-side.
   [OdiloAPIClient.requestExternalLoginURL()]

3. App opens that URL in ASWebAuthenticationSession — a real system browser sheet,
   entirely outside this app's own networking code:

   3a. Browser → KB   GET /si/auth/oauth2.0/v1/authorize?...&state=<generated>
       KB → Browser   302 → /si/login/?sessionOnly=true&goto=<the same authorize URL>

   3b. Browser → KB   GET /si/login/?goto=...
       KB → Browser   200, login page HTML + JS bundle (a React SPA)

   3c. User types library card number + password into KB's real page — this app
       never sees the password.
       Page JS → KB   POST /si/login/api/authenticate
                      body: {"module":"UsernameAndPassword","definition":{"username","password"}}
       KB → Page      200 {"nextModule":"Success", ...}
                      Set-Cookie: iw_access_token, iwdev, iwopbs (iWelcome session cookies)

   3d. Page re-navigates to the authorize URL again, now carrying the freshly
       authenticated cookies. In the one full trace this was captured from, this
       hop 302'd *back to the login page* rather than completing — see "Known
       unknowns" below. The browser evidently handles whatever this actually
       requires; we only see the network layer, not the SPA's JS logic.

   3e. Eventually: KB → Browser   302 → <callback scheme>://oauth?code=<uuid>&state=<generated>
       iOS intercepts this custom-scheme redirect and routes it directly to
       ASWebAuthenticationSession's completion handler — the app's own
       Info.plist / URL-scheme registration is not involved at all, which is
       one of the reasons this app uses ASWebAuthenticationSession instead of
       replicating steps 3a–3e as raw HTTP calls (see "Why a browser sheet"
       below).
   [LibraryAuthService.runWebAuthSession()]

4. App parses `code` and `state` out of that callback URL.
   Common mixup: `state` (a short CSRF nonce, generated by Odilo in step 2) and
   `code` (a UUID, generated by KB in step 3e) are easy to conflate — they're
   different values with different origins.

5. App → Odilo   POST /opac/api/v2/login/external?type=OAUTH2&client=app
                 Authorization: Bearer <appBearer>
                 body: { state, code, scope: "openid profile",
                         iss: "https://login.kb.nl/si/auth/oauth2.0/v1", client_id: "odiloapp" }
   Odilo → App   { id: <patronId>, accessToken: <patronToken>, refreshToken,
                   session: <matches JSESSIONID from #1>, expiresIn: 14399, name, email }
   [OdiloAPIClient.completeExternalLogin()]

6. App stores patronId / appToken+expiry / patronToken+expiry / refreshToken / name / email
   → LibraryCredentials → Keychain, via CredentialsStore.

7. From here on:
   - Every call sends  Authorization: Bearer <appToken>
   - Checkout additionally sends  OAuth-Token: <patronToken>
   - JSESSIONID/AWSALB/AWSALBCORS just ride along via URLSession.shared's cookie jar,
     seeded back in step 1 and refreshed by Set-Cookie on every response since.
```

Steps 1, 2, and 5 are this app's own `OdiloAPIClient`/`LibraryAuthService`
code. Step 3 is entirely KB's own page running inside the system browser
sheet.

## Why a browser sheet instead of replicating the KB login form

An earlier version of this integration tried replicating steps 3a–3c as raw
`URLSession` calls (matching headers/cookies/body exactly). The login POST
itself (3c) worked fine and returned `nextModule: "Success"`. The *next*
step — re-hitting the authorize URL with the newly-authenticated cookies —
looped back to the login page instead of completing, for reasons that were
never fully diagnosed. The likely cause: KB's login page is a JS-driven SPA
doing something (local storage, timing, an extra request, session
"warm-up") that a bare HTTP replay doesn't reproduce, because proxy capture
only shows network traffic, not what the page's JavaScript actually does.

`ASWebAuthenticationSession` sidesteps this entirely: it renders KB's real
page in a real browser context, so whatever that page needs — this redirect
dance, a future MFA step, a ToS screen, anything — just works, and iOS
hands the final callback URL back automatically without this app needing to
register a URL scheme or intercept anything itself. The tradeoff is a
system-styled sheet instead of an in-app form, and the password is
literally never in this app's process — both are considered acceptable
given the alternative is fragility against any future change to KB's login
page.

## Known unknowns

These are open items, not solved problems — don't assume behavior for any
of them without a fresh capture confirming it:

1. **Patron token refresh is unconfirmed.** `refreshToken` is stored
   (`LibraryCredentials.patronRefreshToken`) but nothing calls it — no
   refresh request has been captured yet. Leading hypothesis: the same
   `POST /opac/api/v2/token/` endpoint, with
   `grant_type=refresh_token&refresh_token=<token>` instead of
   `client_credentials`, since it's already confirmed to be a real
   multi-grant-type OAuth2 token endpoint. Unconfirmed. To verify: capture
   traffic ~4+ hours after a real login and watch for either a proactive
   refresh call before a normal request, or a failed request followed by a
   refresh-shaped one and a retry. It's also entirely possible the official
   app doesn't implement silent refresh at all and just forces a full
   re-login — that would be a legitimate answer too, and this app's current
   fallback (surface an auth error, prompt to log in again) already covers
   it.
2. **The step 3d redirect loop is unexplained.** It resolved itself in the
   one full trace this was built from, but *why* it looped once before
   completing was never determined. Not a blocker (the browser sheet
   handles it transparently either way), but worth knowing if login ever
   seems to hang or take an extra visible step.
3. **A custom callback URL scheme is untested.** Step 2's `callback`
   parameter is confirmed to be echoed back verbatim by Odilo, which
   strongly suggests this app could pass its own URL scheme instead of
   reusing the official app's `online.bibliotheek://oauth`. That would
   avoid any theoretical ambiguity if both apps are installed on the same
   device. Nobody has tried it against a real response yet — `LibraryAuthService`
   currently reuses the known-good `online.bibliotheek` scheme deliberately,
   documented inline as the "known-good option."
