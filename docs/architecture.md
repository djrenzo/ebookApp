# Architecture

## Project structure

```
project.yml                          XcodeGen config — source of truth for the Xcode project
LibraryCheckoutManager.xcodeproj/     Generated by `xcodegen generate` — don't hand-edit
public/icon.svg                      App icon source, rendered to AppIcon.png in CI
.github/workflows/build-ios.yml      Manual (workflow_dispatch) unsigned-archive + GitHub Release build

LibraryCheckoutManager/
  App/            @main entry point (LibraryCheckoutManagerApp.swift) → RootTabView
  Models/         Plain data types, mostly Decodable API response shapes
  Services/       Stateless-ish API/IO clients (network, Keychain, filesystem, auth)
  ViewModels/     @MainActor @Observable classes, one per screen (or shared, see below)
  Views/          SwiftUI views
  Theme/          Shared colors/gradients (LibraryTheme)
```

XcodeGen regenerates the whole `.xcodeproj` from `project.yml` on every CI
build (`xcodegen generate`). New Swift files under `LibraryCheckoutManager/`
are picked up automatically by XcodeGen's folder-based `sources:` entry — no
manual "add file to target" step, no `.pbxproj` editing needed.

## Screens (RootTabView's four tabs)

1. **Library** (`LibraryListView`) — the patron's current checkouts, with
   per-book download/read actions. Backed by the *shared*
   `LibraryViewModel` (see below).
2. **Search** (`SearchView`) — catalog search (not just checkouts), with
   offset-based infinite scroll pagination. Tapping a result pushes
   `BookDetailView`, which has its own "Checkout" button.
3. **Downloads** (`DownloadsListView`) — locally saved EPUBs, independent of
   live checkout state (a book stays here after it's returned/expired).
4. **Settings** (`SettingsView`) — Log In / Log Out, plus a debugging
   section (opt-in in-memory network request log).

## Shared vs. per-screen view models

`LibraryViewModel` is the one exception to "one view model per screen": it's
created once in `RootTabView` and injected via `.environment(libraryViewModel)`,
so both `LibraryListView` and `BookDetailView` (pushed from the *Search* tab)
read the same instance. This matters because checking out a book from Search
needs to update the Library tab's checkout list — `BookDetailView` calls
`libraryViewModel.loadCheckouts()` on a successful checkout, and because it's
the same `@Observable` instance the Library tab is already reading from,
that list refreshes immediately even before the user switches tabs.

Every other view model (`SearchViewModel`, `BookDetailViewModel`,
`DownloadsViewModel`) is owned locally by its view via `@State`.

## Key services

- **`OdiloAPIClient`** — the library API client. Every method mirrors a
  specific captured request (see `docs/odilo-api.md`). All requests go
  through `URLSession.shared`, deliberately, so its cookie jar picks up
  `Set-Cookie` responses automatically — no method builds a `Cookie` header
  by hand. Every request/response is reported to `RequestLogger` regardless
  of outcome.
- **`LibraryAuthService`** — orchestrates the full login flow (app token →
  KB login URL → `ASWebAuthenticationSession` → code exchange) and exposes
  `validCredentials()`, which transparently refreshes the app-level token
  when expired. See `docs/auth-flow.md` for the full sequence.
- **`CredentialsStore`** — Keychain-backed (`actor`, `AfterFirstUnlockThisDeviceOnly`
  accessibility). `load()` returns `LibraryCredentials?` — `nil` means "not
  logged in," which is the normal state until `LibraryAuthService.login()`
  succeeds once. No seeded/fallback credentials exist anywhere.
- **`EbookFileStore`** — saves EPUBs under `Documents/Ebooks/`, which is
  exposed as a browsable folder in the iOS Files app via
  `UIFileSharingEnabled` + `LSSupportsOpeningDocumentsInPlace` in
  `project.yml`. Its `manifest.json` bookkeeping file lives in *Application
  Support* instead (not Documents), specifically so the user-visible Files
  folder only ever contains their actual books, not app metadata.
- **`EPUBOpener`** — hands a downloaded EPUB to Apple Books (or whatever
  else claims the EPUB document type) via `UIDocumentInteractionController`'s
  "Open In" menu. This is the closest thing to an automatic handoff iOS
  allows a sandboxed app to do — there's no way to silently launch another
  app with a file with zero user interaction. Both `LibraryListView` and
  `DownloadsListView` fall back to the old QuickLook preview if
  `EPUBOpener` reports no compatible app is installed.
- **`RequestLogger`** — opt-in (`Settings → Log network requests`),
  in-memory only (nothing written to disk), and redacts `Authorization`/
  `Cookie`/`Set-Cookie` header values before storing an entry, keeping only
  a short suffix. This is the primary on-device debugging tool for auth
  issues — turn it on, reproduce, check `Settings → View Request Log`.

## Conventions worth preserving

- **Decodable models are lenient about optional/missing fields on purpose.**
  The Odilo API mixes ebooks, audiobooks, and reading lists in the same
  response shape (e.g. `SearchRecord`), so most models use a custom
  `init(from:)` that only requires `id`/`title` and defaults everything else,
  rather than a synthesized `Decodable` that would throw on a single missing
  field partway through a page of results.
- **Errors are a single `LocalizedError` enum per concern**
  (`LibraryAPIError`, `LibraryAuthError`) rather than per-call error types,
  and view models surface `errorDescription` directly to the UI via
  `LibraryErrorBanner`.
- **No dependency on third-party packages.** Everything — networking,
  Keychain, EPUB handoff — uses first-party Apple frameworks
  (`Foundation`, `Security`, `AuthenticationServices`, `UIKit`,
  `UniformTypeIdentifiers` via `UIDocumentInteractionController`). If a
  future feature seems to need a package, that's worth pausing on, not
  defaulting into.
